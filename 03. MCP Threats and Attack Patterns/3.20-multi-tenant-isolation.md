# 3.20 Multi-Tenant and Cross-Tenant Isolation (`TNNT`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

Multi-tenant MCP deployments share server infrastructure, caching layers, credential stores, and sometimes model context across organizational boundaries. **Tenant isolation** is the set of controls that prevents one tenant's data, credentials, tool results, and context from reaching another tenant. A failure here is a data breach by definition — not a misconfiguration to fix later.

## Why this category matters

SaaS platforms increasingly expose MCP servers that serve multiple organizations from a single deployment. A tenant isolation failure means Tenant A's confidential data — project tasks, source code, customer records, credentials — becomes visible to Tenant B without any exploit beyond normal MCP operations. The Asana incident (June 2025) proved this is not theoretical: a logic flaw in their experimental MCP server caused cross-organization exposure of tasks, projects, teams, comments, and files.

## Scope

Tenant data separation, cross-tenant resource access, credential isolation, context bleed between tenant sessions, cache isolation, tenant-scoped logging, and server instance isolation in shared deployments.

## When to prioritize

Critical when the MCP server under test serves more than one organization, team, or tenant from a shared instance — whether that is a SaaS platform, an enterprise gateway, or a shared internal deployment.

## Related categories

[AUTHZ](3.04-authorization-permission.md), [RSRC](3.06-resource-data-access.md), [CTX](3.08-context-memory.md), [SECR](3.17-secrets-credentials.md), [PRVC](3.19-privacy-retention.md), [GOV](3.14-enterprise-governance.md)

## Common test chains

TNNT-01 (data isolation) + RSRC-03 (cross-workspace access); TNNT-03 (IDOR) + AUTHZ-03 (cross-user resource access); TNNT-02 (context bleed) + CTX-01 (context injection); TNNT-04 (credential isolation) + SECR-01 (secret leakage); TNNT-05 (cache poisoning) + OUTV-02 (output handling).

## Threats and attack patterns

Tenant isolation tests look for data, context, credentials, or cached results that cross an organizational boundary through the MCP layer. The cases below are drawn from public incidents and known architectural patterns in multi-tenant AI platforms.

### Cross-organization data exposure through shared MCP server

The [Asana MCP server data exposure bug](https://www.bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/) (June 2025) is the canonical public incident. Asana's experimental MCP server had a logic flaw that caused incomplete tenant isolation. The result: task, project, team, comment, discussion, and file data from one organization could be exposed to MCP users in another organization. Asana took the MCP feature offline on approximately June 5, 2025, fixed the code, reset all connections, and required manual reconnection. Affected customers were notified around June 16–18, 2025.

The root cause was not a sophisticated attack — it was a logic flaw in how the server scoped queries to the requesting tenant. In multi-tenant MCP servers, every data-returning path must enforce tenant scoping. A single missed filter on a single query is enough.

**Tests:** `MCPSTG-TNNT-01`, `MCPSTG-TNNT-03`, `MCPSTG-TNNT-06`.

### Context and session bleed across tenants

When a shared MCP server maintains in-memory state — conversation context, tool result caches, or session objects — a missing or incorrect tenant partition can cause Tenant A's context to bleed into Tenant B's session. This is distinct from a data-access flaw: the data was correctly fetched for Tenant A, but it persists in a shared buffer and is served to Tenant B on the next request.

This pattern is especially dangerous with model context windows. If tool results or resource content from Tenant A remain in a shared context object, the model may reference or summarize Tenant A data when responding to Tenant B.

**Tests:** `MCPSTG-TNNT-02`, `MCPSTG-TNNT-05`.

### Credential pool sharing across tenants

Multi-tenant servers that use a shared credential pool (a single service account, a shared OAuth client, or a common API key) for downstream API calls create a privilege confusion risk. Tenant A's request may execute with Tenant B's credentials if the credential dispatch logic does not enforce strict tenant-to-credential mapping. Even when the server uses per-tenant credentials, if the mapping is based on a client-supplied tenant identifier without server-side validation, an attacker can claim a different tenant's identity.

**Tests:** `MCPSTG-TNNT-04`.

### Tenant ID enumeration and IDOR

Multi-tenant MCP servers that use predictable tenant identifiers (sequential integers, simple slugs, or organization names) in resource URIs, tool parameters, or session headers are vulnerable to enumeration. An authenticated tenant can guess or iterate over other tenant identifiers to access their data. This is the MCP-specific variant of Broken Object Level Authorization (BOLA/IDOR).

**Tests:** `MCPSTG-TNNT-03`.

### Canonical attack patterns

#### Cross-Tenant Data Leakage

**Tests:** `MCPSTG-TNNT-01`, `MCPSTG-TNNT-03`.

A tenant-authenticated session issues a `tools/call` or `resources/read` request referencing another tenant's object. The server executes the request without verifying that the authenticated tenant owns the referenced object.

##### Impact

* Full read (and potentially write) access to another organization's data.
* Regulatory breach (GDPR, HIPAA, SOC 2) on first occurrence.
* Reputational damage — see Asana incident response timeline.

##### Red flags

* Resource URIs that contain a tenant identifier as a path segment or query parameter.
* Tool parameters that accept an organization ID, team ID, or workspace ID without server-side validation.
* Shared database connections without row-level security or tenant-scoped queries.
* API responses that include a `tenant_id` or `org_id` field the caller did not supply.

##### Defensive guidance

* Enforce tenant scoping at the data layer (row-level security, scoped database connections, or query filters applied before user-supplied parameters).
* Never trust a client-supplied tenant identifier — derive tenant identity from the authenticated session.
* Audit every data-returning code path for missing tenant filters.
* Run cross-tenant access tests as part of CI/CD for every MCP server release.

#### Context Contamination

**Tests:** `MCPSTG-TNNT-02`, `MCPSTG-TNNT-05`.

Shared caches, in-memory stores, or model context windows retain Tenant A's data and serve it to Tenant B.

##### Impact

* Confidential data from one tenant appears in another tenant's model responses.
* Cached tool results from Tenant A influence Tenant B's decisions.
* Difficult to detect because the data appears as normal model output.

##### Red flags

* Shared in-memory caches without tenant-scoped keys.
* Model context that is not cleared between tenant sessions.
* Tool result caching that uses tool name + parameters as the key without including tenant ID.
* Session objects that persist beyond a single tenant's request lifecycle.

##### Defensive guidance

* Partition all caches by tenant ID.
* Clear model context completely between tenant sessions.
* Include tenant ID in all cache keys.
* Use separate process or container instances per tenant where feasible.

### MCPSTG-TNNT-01 — Test Tenant Data Isolation in Shared MCP Servers

<a id="mcpstg-tnnt-01"></a>

#### Summary

Verify that a shared MCP server instance enforces strict tenant data isolation: an authenticated session for Tenant A cannot read, list, or modify data belonging to Tenant B through any tool or resource endpoint.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` authenticated as Tenant A; `<TEST_USER_B>` authenticated as Tenant B on the same shared MCP server.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` configured as a multi-tenant instance under `<TEST_WORKSPACE>`.
- **Tools/resources:** `<TEST_TOOL_NAME>`, `<TEST_RESOURCE>` (synthetic lab fixtures with tenant-scoped data).
- **Trust boundary:** Tenant A session ↔ shared MCP server ↔ Tenant A data store; Tenant B session ↔ same server ↔ Tenant B data store.
- **Attacker position:** Authenticated as Tenant A, attempting to access Tenant B data through normal MCP operations.
- **Potential impact:** Full cross-organization data breach. Regulatory violation.

#### Test Objectives

- Confirm that `tools/call` responses for Tenant A never contain Tenant B data.
- Confirm that `resources/list` and `resources/read` for Tenant A never expose Tenant B resources.
- Confirm that write operations from Tenant A cannot modify Tenant B objects.
- Document any tenant scoping mechanism (query filter, row-level security, database isolation).

#### Preconditions

- Authorized lab environment and written scope.
- Two distinct tenant accounts (`<TEST_USER_A>`, `<TEST_USER_B>`) on the shared MCP server.
- Known synthetic data seeded into both tenants (distinct, identifiable records).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review server source code for tenant scoping logic. Identify every data-returning code path (tool handlers, resource providers). Verify each path includes a tenant filter derived from the authenticated session, not from client-supplied parameters.

##### 2. Configuration Review

Inspect database connection configuration: is it a shared database with tenant column filters, separate schemas, or separate databases? Check for row-level security policies. Verify that the MCP server derives tenant identity from the authentication token, not from a request header or parameter.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A) to `<AUTHORIZED_LAB_SERVER>`.
2. List all resources visible to Tenant A:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "resources/list"
}
```

3. Verify response contains only Tenant A resources. Record resource URIs.
4. Call each data-returning tool with Tenant A credentials:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "list all records",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

5. Verify response contains only Tenant A data. Search response body for any Tenant B identifiers.
6. Repeat steps 1–5 authenticated as `<TEST_USER_B>` (Tenant B). Cross-check: no Tenant A data in Tenant B responses.

##### 4. Abuse Case Testing

- Supply Tenant B's known resource URIs in Tenant A's `resources/read` request — expect deny.
- Supply Tenant B's known object IDs in Tenant A's `tools/call` parameters — expect deny or empty result.
- Attempt write operations targeting Tenant B objects from Tenant A session — expect deny.

##### 5. Log and Detection Review

Confirm that cross-tenant access attempts generate audit log entries with: requesting tenant ID, target resource/object, decision (deny), timestamp, and correlation ID. Verify logs do not expose Tenant B data in the denial record.

#### Example snippets

Lab host configuration for multi-tenant testing:

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "url": "https://<TEST_WORKSPACE>/mcp/v1",
      "headers": {
        "Authorization": "Bearer <TEST_TOKEN_TENANT_A>"
      }
    }
  }
}
```

Cross-tenant resource read attempt:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "resources/read",
  "params": {
    "uri": "resource://<TEST_WORKSPACE>/tenant-b/projects/proj-001"
  }
}
```

Cross-tenant tool call attempt:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "project_id": "<TENANT_B_PROJECT_ID>",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures. Seed both tenants with distinct, identifiable records (e.g., Tenant A: `project-alpha-001`, Tenant B: `project-beta-001`).

#### Expected Results

- **Secure:** Every data-returning endpoint returns only the requesting tenant's data. Cross-tenant resource reads return 403 or empty. Cross-tenant tool calls return authorization errors. Audit logs capture the denial.
- **Insecure:** Tenant A receives Tenant B data in tool responses, resource listings, or resource reads. Write operations succeed against Tenant B objects.
- **Evidence:** Redacted tool call responses showing tenant-scoped (or unscoped) data, resource listings, audit log entries for cross-tenant attempts.

#### Remediation

- Derive tenant identity from the authenticated session token — never from client-supplied parameters.
- Apply tenant filters at the data layer (row-level security, scoped connections, or mandatory query predicates).
- Audit every data-returning code path for missing tenant scoping before each release.
- Implement automated cross-tenant access tests in CI/CD.

#### Tools

MCP client utilities (raw JSON-RPC), HTTP/TLS interception proxy, structured log search, policy-as-code test harness (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-TNNT-02 — Test Tenant Context Separation

<a id="mcpstg-tnnt-02"></a>

#### Summary

Verify that model context, conversation state, and in-memory session data from one tenant's MCP interactions do not bleed into another tenant's session on a shared server instance. Context bleed can cause Tenant B to receive summaries, references, or direct content from Tenant A's prior interactions.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` (Tenant A) and `<TEST_USER_B>` (Tenant B) on sequential or concurrent sessions to the same shared MCP server.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, multi-tenant.
- **Trust boundary:** Tenant A session context ↔ shared server memory ↔ Tenant B session context.
- **Attacker position:** Tenant B observes context that originated in Tenant A's session.
- **Potential impact:** Confidential business data from Tenant A appears in Tenant B's model context or tool responses.

#### Test Objectives

- Confirm that server-side session state is fully partitioned per tenant.
- Confirm that model context from Tenant A's tool calls does not persist into Tenant B's session.
- Confirm that in-memory caches, buffers, or conversation history are cleared or isolated between tenants.

#### Preconditions

- Authorized lab environment and written scope.
- Two distinct tenant accounts with sequential session capability.
- Ability to inspect server-side memory or session state (debugger, instrumentation, or log-level evidence).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review server code for session management. Identify where session state, conversation context, and tool result history are stored. Verify that session objects are keyed by tenant ID and destroyed or isolated between tenant sessions.

##### 2. Configuration Review

Check session configuration: in-memory, Redis, database-backed? Verify session keys include tenant ID. Check TTL and cleanup behavior. Verify that model context is not shared across sessions.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A).
2. Execute a tool call with distinctive synthetic data:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "TENANT_A_CANARY_STRING_abc123",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

3. Record the response. End Tenant A session.
4. Authenticate as `<TEST_USER_B>` (Tenant B) on the same server instance.
5. Execute a broad query tool call:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "show recent activity",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

6. Search Tenant B's response for `TENANT_A_CANARY_STRING_abc123` or any Tenant A data.
7. Repeat with concurrent sessions if the server supports them.

##### 4. Abuse Case Testing

- Rapidly alternate between Tenant A and Tenant B sessions to test race conditions in session cleanup.
- Send requests that reference conversation history or prior tool results — verify no cross-tenant references.

##### 5. Log and Detection Review

Check server logs for session lifecycle events (create, use, destroy). Verify session IDs are tenant-scoped. Look for any log entries where a session serves requests from two different tenants.

#### Example snippets

Canary tool call for Tenant A:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "content": "CANARY_TENANT_A_ISOLATION_TEST_20261018",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

Broad query from Tenant B looking for bleed:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "show all recent context",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures. Use unique canary strings per tenant for identification.

#### Expected Results

- **Secure:** Tenant B session contains zero references to Tenant A's canary string or data. Session state is fully isolated. Server logs show clean session lifecycle.
- **Insecure:** Tenant A's canary string or data appears in Tenant B's tool responses, context, or model output. Session state is shared or incompletely cleared.
- **Evidence:** Redacted tool responses from both tenants, server session logs, memory inspection results.

#### Remediation

- Partition all server-side session state by tenant ID.
- Clear or destroy session objects completely when a tenant session ends.
- Use separate model context windows per tenant — never share context across tenants.
- Implement session isolation tests in CI/CD with canary-based detection.

#### Tools

MCP client utilities, HTTP/TLS interception proxy, structured log search (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-TNNT-03 — Test Cross-Tenant Resource Access via Direct ID Reference

<a id="mcpstg-tnnt-03"></a>

#### Summary

Test whether an authenticated tenant can access another tenant's resources by directly referencing their object IDs, resource URIs, or entity identifiers in MCP requests. This is the MCP-specific variant of Broken Object Level Authorization (BOLA/IDOR).

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` authenticated as Tenant A.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, multi-tenant.
- **Tools/resources:** Tools and resources that accept object identifiers (project IDs, document IDs, record IDs).
- **Trust boundary:** Tenant A session ↔ shared MCP server ↔ Tenant B data objects.
- **Attacker position:** Tenant A knows or guesses Tenant B's object IDs and supplies them in tool calls or resource reads.
- **Potential impact:** Unauthorized read or write access to another tenant's specific objects.

#### Test Objectives

- Confirm that the server validates object ownership against the authenticated tenant before returning data.
- Confirm that predictable or sequential IDs cannot be enumerated to discover other tenants' objects.
- Document the authorization check mechanism (server-side tenant filter, object-level ACL, or none).

#### Preconditions

- Authorized lab environment and written scope.
- Two tenant accounts with known synthetic object IDs in each tenant.
- Knowledge of the ID format used by the server (UUIDs, sequential integers, slugs).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review server code for object-level authorization. For each tool handler that accepts an object ID, verify it checks that the object belongs to the authenticated tenant before returning data.

##### 2. Configuration Review

Check ID generation: sequential integers are high risk. Verify that object-level authorization is enforced in the data layer, not only in the API layer.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A).
2. Record known Tenant B object IDs from lab setup (e.g., `<TENANT_B_PROJECT_ID>`).
3. Request Tenant B's resource directly:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "resources/read",
  "params": {
    "uri": "resource://<TEST_WORKSPACE>/projects/<TENANT_B_PROJECT_ID>"
  }
}
```

4. Call a tool with Tenant B's object ID:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "project_id": "<TENANT_B_PROJECT_ID>",
      "action": "read"
    }
  }
}
```

5. Expect: 403, empty result, or error indicating unauthorized access.
6. If IDs are sequential, attempt ID enumeration: increment/decrement known IDs.

##### 4. Abuse Case Testing

- Enumerate IDs by incrementing known Tenant A IDs to find Tenant B objects.
- Attempt write operations with Tenant B object IDs from Tenant A session.
- Test batch/bulk endpoints that accept lists of IDs — mix Tenant A and Tenant B IDs.

##### 5. Log and Detection Review

Verify that cross-tenant ID access attempts are logged with: requesting tenant, target object ID, decision, and timestamp. Check for rate limiting on enumeration patterns.

#### Example snippets

IDOR attempt via tool call:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "record_id": "<TENANT_B_RECORD_ID>",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

ID enumeration attempt:

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "record_id": "1001",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures. Seed tenants with known IDs: Tenant A owns IDs 1–100, Tenant B owns IDs 101–200.

#### Expected Results

- **Secure:** All cross-tenant ID references return 403 or empty. Enumeration attempts are rate-limited and logged. Object ownership is validated server-side.
- **Insecure:** Tenant A receives Tenant B's data by supplying Tenant B's object ID. Sequential IDs enable enumeration.
- **Evidence:** Redacted tool responses, resource read results, audit log entries for cross-tenant access attempts.

#### Remediation

- Validate object ownership against the authenticated tenant for every object-level operation.
- Use non-sequential, non-predictable identifiers (UUIDs v4 or similar).
- Implement rate limiting on ID-parameterized endpoints to slow enumeration.
- Add automated IDOR tests to CI/CD with cross-tenant object ID injection.

#### Tools

MCP client utilities, HTTP/TLS interception proxy, structured log search, rate-limit exercise tooling (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-TNNT-04 — Test Tenant Credential and Token Isolation

<a id="mcpstg-tnnt-04"></a>

#### Summary

Verify that credentials, tokens, and API keys used by the MCP server for downstream service calls are strictly scoped to the requesting tenant. A shared credential pool or incorrect credential dispatch can cause Tenant A's requests to execute with Tenant B's permissions on downstream services.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` (Tenant A) and `<TEST_USER_B>` (Tenant B) on the same shared MCP server.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, multi-tenant, connecting to downstream APIs.
- **Trust boundary:** MCP server credential store ↔ downstream API ↔ tenant-scoped data.
- **Attacker position:** Tenant A's requests execute with Tenant B's downstream credentials due to credential dispatch flaw.
- **Potential impact:** Unauthorized access to Tenant B's downstream services, data, and operations.

#### Test Objectives

- Confirm that each tenant's MCP requests use only that tenant's credentials for downstream calls.
- Confirm that the credential dispatch mechanism is based on server-validated tenant identity.
- Confirm that credential storage is partitioned — Tenant A cannot read Tenant B's stored tokens.

#### Preconditions

- Authorized lab environment and written scope.
- Two tenant accounts with distinct downstream credentials.
- Ability to observe downstream API calls (proxy, logging, or downstream audit trail).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review credential storage and dispatch code. Verify that downstream API credentials are stored per-tenant and selected based on authenticated tenant identity. Check for shared service accounts or single-credential patterns.

##### 2. Configuration Review

Inspect credential storage (vault, environment variables, config file). Verify per-tenant credential entries. Check for a single shared API key serving all tenants.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A).
2. Execute a tool that makes downstream API calls:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "action": "list_resources",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

3. Capture the downstream API call (via proxy or downstream logs). Record the credential used (redact in evidence).
4. Repeat as `<TEST_USER_B>` (Tenant B). Verify a different credential is used for the downstream call.
5. Compare: if both tenants' requests use the same downstream credential, isolation is broken.

##### 4. Abuse Case Testing

- Attempt to supply a tenant identifier parameter that would select a different tenant's credentials.
- Test credential caching: after Tenant A's request, does Tenant B's request reuse Tenant A's cached credential?

##### 5. Log and Detection Review

Verify audit logs include: tenant ID, downstream service called, credential identifier used (not the credential itself), and timestamp. Check for credential reuse across tenants.

#### Example snippets

Tool call triggering downstream API:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "action": "fetch_external_data",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures. Configure lab downstream APIs to echo the credential identifier in responses for testing.

#### Expected Results

- **Secure:** Each tenant's downstream calls use only that tenant's credentials. Credential storage is partitioned. No shared service account for tenant-scoped operations.
- **Insecure:** Both tenants' requests use the same downstream credential, or Tenant A's request uses Tenant B's credential. Credential dispatch is based on client-supplied tenant identifier.
- **Evidence:** Redacted downstream API logs showing credential identifiers per tenant, proxy captures, server audit logs.

#### Remediation

- Store credentials per-tenant in a vault or partitioned secret store.
- Dispatch credentials based on server-validated tenant identity, never client-supplied parameters.
- Audit credential usage logs for cross-tenant credential sharing.
- Rotate credentials on any suspected cross-tenant credential exposure.

#### Tools

MCP client utilities, HTTP/TLS interception proxy, egress observer, structured log search (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-TNNT-05 — Test Cache Poisoning Across Tenant Boundaries

<a id="mcpstg-tnnt-05"></a>

#### Summary

Verify that cached tool results, resource content, and computed values are partitioned by tenant. A shared cache without tenant-scoped keys allows Tenant A's cached data to be served to Tenant B, causing data leakage or decision poisoning.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` (Tenant A) and `<TEST_USER_B>` (Tenant B) on sequential sessions.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, multi-tenant with caching enabled.
- **Trust boundary:** Tenant A tool result → shared cache → Tenant B tool response.
- **Attacker position:** Tenant A populates the cache with data that Tenant B subsequently receives.
- **Potential impact:** Cross-tenant data leakage via cache. Decision poisoning if cached results influence Tenant B's model behavior.

#### Test Objectives

- Confirm that all cache keys include tenant ID.
- Confirm that cache hits for Tenant B never return Tenant A's cached data.
- Confirm that cache invalidation is tenant-scoped.

#### Preconditions

- Authorized lab environment and written scope.
- Two tenant accounts on a shared MCP server with caching enabled.
- Ability to identify cache hits vs. cache misses (response headers, timing, or server instrumentation).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review caching implementation. Identify cache key composition: does it include tenant ID? Check all cache layers: in-memory, Redis, CDN, database query cache.

##### 2. Configuration Review

Inspect cache configuration. Check TTL, eviction policy, and key format. Verify tenant ID is a mandatory component of every cache key.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A).
2. Execute a tool call that will be cached:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "project summary",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

3. Record the response (contains Tenant A data).
4. Authenticate as `<TEST_USER_B>` (Tenant B).
5. Execute the same tool call with the same parameters:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "project summary",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

6. Compare: if Tenant B receives Tenant A's data (or a mix), cache isolation is broken.
7. Check response timing: a suspiciously fast response for Tenant B on a first request may indicate a shared cache hit.

##### 4. Abuse Case Testing

- Tenant A deliberately populates cache with canary data, then Tenant B reads the same cache path.
- Test cache invalidation: Tenant A updates data — does Tenant B's cache still serve stale Tenant A data?

##### 5. Log and Detection Review

Verify cache hit/miss logs include tenant ID. Check for cache entries that serve cross-tenant data.

#### Example snippets

Same-parameter call from two tenants:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "query": "CACHE_TEST_QUERY_001",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

#### Expected Results

- **Secure:** Tenant B receives only Tenant B data, even when the same query was recently cached for Tenant A. Cache keys include tenant ID. Cache hits are tenant-scoped.
- **Insecure:** Tenant B receives Tenant A's cached tool results or resource content. Cache keys do not include tenant ID.
- **Evidence:** Redacted tool responses from both tenants, cache inspection (key format), response timing analysis.

#### Remediation

- Include tenant ID as a mandatory component of every cache key.
- Partition cache storage by tenant (separate namespaces, prefixes, or instances).
- Implement tenant-scoped cache invalidation.
- Add automated cache isolation tests to CI/CD.

MCP client utilities, HTTP/TLS interception proxy, structured log search (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-TNNT-06 — Test Tenant-Scoped Logging and Audit Trail

<a id="mcpstg-tnnt-06"></a>

#### Summary

Verify that MCP server audit logs are scoped per tenant: each tenant's log entries are isolated, queryable, and do not expose another tenant's activity, data, or identifiers. Shared log streams without tenant partitioning create cross-tenant information disclosure and compliance failures.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` (Tenant A) and `<TEST_USER_B>` (Tenant B) on the same shared MCP server.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, multi-tenant.
- **Trust boundary:** Tenant A log entries ↔ shared log storage ↔ Tenant B log access.
- **Attacker position:** Tenant A gains access to log data revealing Tenant B's activity.
- **Potential impact:** Cross-tenant activity disclosure, compliance failure (SOC 2, GDPR).

#### Test Objectives

- Confirm that each tenant can only query their own audit log entries.
- Confirm that log entries include tenant ID and do not contain another tenant's sensitive data.
- Confirm that log export and search are tenant-scoped.

#### Preconditions

- Authorized lab environment and written scope.
- Two tenant accounts that generate audit log entries.
- Access to log query interfaces or APIs.
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review logging implementation. Verify that every log entry includes a tenant ID field. Check log storage and query mechanisms for tenant filtering.

##### 2. Configuration Review

Inspect log aggregation configuration. Verify tenant-based access controls on log query interfaces. Check that log export functions enforce tenant scoping.

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A). Execute several tool calls to generate audit entries.
2. Authenticate as `<TEST_USER_B>` (Tenant B). Execute several tool calls to generate audit entries.
3. As Tenant A, query audit logs:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "audit_log_query",
    "arguments": {
      "filter": "all",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

4. Verify Tenant A's log query returns only Tenant A entries.
5. Search for Tenant B identifiers in Tenant A's log results.

##### 4. Abuse Case Testing

- Attempt to query logs with Tenant B's tenant ID from Tenant A's session.
- Attempt broad log queries without tenant filters — expect server to inject tenant filter.

##### 5. Log and Detection Review

Confirm that cross-tenant log access attempts are themselves logged.

#### Example snippets

Tenant-scoped log query:

```json
{

  "method": "tools/call",
  "params": {
    "name": "audit_log_query",

      "start_time": "2026-10-18T00:00:00Z",
      "end_time": "2026-10-18T23:59:59Z",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

#### Expected Results

- **Secure:** Each tenant's log queries return only their own entries. Log entries include tenant ID. Cross-tenant log queries are blocked.
- **Insecure:** Tenant A can see Tenant B's activity in audit logs. Log entries lack tenant ID. Broad queries return mixed-tenant results.
- **Evidence:** Redacted log query results from both tenants, log schema showing tenant ID field, access control configuration.

#### Remediation

### MCPSTG-TNNT-07 — Test MCP Server Instance Isolation in SaaS Deployments

<a id="mcpstg-tnnt-07"></a>

#### Summary

Verify that a SaaS MCP deployment provides adequate process-level or instance-level isolation between tenants. Shared-process deployments where all tenants run in the same OS process, memory space, and network namespace increase the blast radius of any single-tenant compromise.

#### Scenario

- **MCP host/client:** `<TEST_USER_A>` (Tenant A) and `<TEST_USER_B>` (Tenant B) on the same SaaS MCP deployment.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` under `<TEST_WORKSPACE>`, SaaS multi-tenant.
- **Trust boundary:** Tenant A process/container ↔ orchestration layer ↔ Tenant B process/container.
- **Attacker position:** Tenant A attempts to observe or influence Tenant B's server process (shared memory, shared filesystem, shared network).
- **Potential impact:** Cross-tenant code execution, data access via shared process memory, side-channel attacks.

#### Test Objectives

- Document the isolation model: shared process, separate processes, separate containers, separate VMs.
- Confirm that Tenant A cannot observe Tenant B's server process, memory, filesystem, or network traffic.
- Confirm that resource limits (CPU, memory, network) are enforced per tenant.
- Confirm that a crash or resource exhaustion in Tenant A's workload does not affect Tenant B.

#### Preconditions

- Authorized lab environment and written scope.
- Two tenant accounts on the shared deployment.
- Infrastructure-level access for observing isolation (container runtime, process list, network namespace).
- Log access for host, gateway, and MCP server.

#### How to Test

##### 1. Manual Review

Review deployment architecture documentation. Identify the isolation model: shared process with tenant threads, separate processes, containers, or VMs. Review container/VM configuration for namespace isolation, resource limits, and network policies.

##### 2. Configuration Review

Inspect container orchestration config (if applicable): are tenants in separate namespaces? Are resource limits (CPU, memory) set per tenant? Are network policies restricting inter-tenant traffic? Is the filesystem isolated per tenant?

##### 3. Runtime Testing

1. Authenticate as `<TEST_USER_A>` (Tenant A).
2. Execute a tool call that triggers a long-running operation:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "action": "compute_intensive_task",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

3. Simultaneously, authenticate as `<TEST_USER_B>` (Tenant B) and execute a normal tool call.
4. Measure: does Tenant A's heavy workload degrade Tenant B's response time?
5. If infrastructure access is available: check process isolation (separate PIDs, namespaces), filesystem isolation (separate mount points), and network isolation (separate network namespaces or policies).

##### 4. Abuse Case Testing

- Tenant A triggers resource exhaustion (large response, long computation) — verify Tenant B is unaffected.
- Tenant A crashes their MCP server process — verify Tenant B's server continues operating.
- Check for shared temp directories, shared log files, or shared socket files between tenants.

##### 5. Log and Detection Review

Verify that infrastructure monitoring captures per-tenant resource usage. Check for alerts on resource exhaustion that could indicate cross-tenant impact.

#### Example snippets

Resource-intensive tool call for isolation testing:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "<TEST_TOOL_NAME>",
    "arguments": {
      "action": "generate_large_report",
      "size": "maximum",
      "workspace": "<TEST_WORKSPACE>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

#### Expected Results

- **Secure:** Tenants run in isolated processes/containers with enforced resource limits. Tenant A's resource exhaustion or crash does not affect Tenant B. No shared filesystem, memory, or network namespace between tenants.
- **Insecure:** Tenants share a process, filesystem, or network namespace. Tenant A's crash takes down Tenant B. Resource exhaustion by one tenant degrades all tenants.
- **Evidence:** Deployment architecture diagram, container/VM configuration, resource limit settings, cross-tenant impact measurements, process isolation evidence.

#### Remediation

- Deploy separate container or process instances per tenant.
- Enforce per-tenant resource limits (CPU, memory, network, disk).
- Use container/VM namespace isolation to prevent cross-tenant process, filesystem, and network visibility.
- Implement health checks and automatic restart per tenant instance.
- Document the isolation model and its limitations in security architecture docs.

MCP client utilities, local process and file-access tracer, sandbox/container runtime with resource and egress limits (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).
