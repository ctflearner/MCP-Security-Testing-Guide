# 3.22 Client-Side and Host Security (`CLNT`)

[← Chapter 3 overview](<3. MCP Threats and Attack Patterns.md>) · [Test case format](test-case-format.md)

## Overview

MCP **clients** and **hosts** are the user-facing components that manage server connections, render tool approval prompts, store credentials, and enforce trust decisions. A compromised or misconfigured client turns every connected MCP server into an attack surface — regardless of how well the server itself is secured. Client-side vulnerabilities let attackers inject rogue servers, bypass approval flows, steal credentials, and break workspace isolation without touching the server at all.

## Why this category matters

Server-side security receives most attention, but the client is the **trust anchor**. It decides which servers to connect, which tools to approve, and which credentials to pass. If the client is subverted — through a malicious config file in a cloned repository, a DNS rebinding attack on a local server, or a plaintext credential store — the entire MCP security model collapses. Published CVEs confirm this is not theoretical: configuration injection in developer tooling has led to remote code execution, and DNS rebinding bypasses have exposed local MCP servers to remote websites.

## Scope

Client and host configuration parsing, workspace-scoped server registration, tool approval UX and policy enforcement, credential storage and isolation, transport validation (TLS, origin, DNS rebinding), auto-install and auto-update flows, workspace-to-workspace isolation.

## When to prioritize

High when the MCP host reads configuration from project-level files (workspace configs, `.mcp.json`, `config.toml`), when developers clone untrusted repositories, when local MCP servers bind to network interfaces, or when multiple projects share a single host installation.

## Related categories

[CONF](3.02-configuration-deployment.md), [AUTHN](3.03-identity-authentication.md), [SECR](3.17-secrets-credentials.md), [TRNS](3.15-transport-channel.md), [SUPP](3.13-supply-chain.md), [TOOL](3.05-tool-security.md)

CLNT-01 (config injection) → TOOL-01 (tool poisoning); CLNT-03 (credential leak) → SECR-01; CLNT-04 (transport validation) → TRNS-01; CLNT-05 (workspace isolation) → RSRC-03 (cross-workspace access).

## Threats and attack patterns

Client-side tests target the gap between what the user intended and what the host actually does. The cases below are configuration-level compromises, approval-flow subversions, and trust-boundary failures at the client layer.

### Project-level configuration as a code-execution vector

[GHSA-xrxf-jgv3-qmrm](https://github.com/advisories/GHSA-xrxf-jgv3-qmrm) (OpenAI Codex CLI ≤ 0.23.0, April 2026) demonstrates the risk. A malicious `.codex/config.toml` file inside a repository could register arbitrary MCP servers. When a developer cloned the repository and ran the CLI, the rogue server launched automatically — with full tool access and no additional user approval. The advisory classifies it as code execution via a project-local MCP configuration.

The pattern generalizes: any MCP host that reads server definitions from workspace-level files is vulnerable if it does not distinguish user-global configuration from project-scoped configuration, or if it fails to prompt the user before trusting a new server definition found in a cloned repo.

**Tests:** `MCPSTG-CLNT-01`, `MCPSTG-CLNT-06`.

### DNS rebinding bypasses local-server protections

[GHSA-w48q-cv73-mx4w / CVE-2025-66414](https://github.com/advisories/GHSA-w48q-cv73-mx4w) (MCP TypeScript SDK, patched in 1.24.0, December 2025) shows that DNS rebinding protection was **off by default** for local Streamable HTTP servers. A malicious website could resolve to `127.0.0.1` after the initial DNS check, gaining access to the local MCP session. The advisory says the attacker could then list tools, call tools, and read resources — all through the user's browser, with no MCP-level authentication.

The rmcp Rust SDK had a parallel advisory ([GHSA-89vp-x53w-74fx](https://github.com/modelcontextprotocol/rust-sdk/security/advisories/GHSA-89vp-x53w-74fx), fixed in 1.4.0) confirming the same class of attack across implementations.

**Tests:** `MCPSTG-CLNT-04`.

### Tool poisoning starts at the client config

Invariant Labs' April 2025 tool-poisoning experiments against Cursor showed that a malicious tool description could instruct the model to read `~/.cursor/mcp.json` and SSH private keys, then place the contents in a tool parameter. The client config file was the exfiltration target because it contained credentials for other MCP servers. The attack required no server-side vulnerability — only a poisoned tool description and a client that stored secrets in a readable config file.

> "The malicious server can instruct Claude to read sensitive data like SSH keys from the user's system"
>
> — Invariant Labs, [MCP Security Notification: Tool Poisoning Attacks](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) (April 2025)

**Tests:** `MCPSTG-CLNT-03`, `MCPSTG-CLNT-05`.

### Cursor MCPoison: IDE extension as attack vector

Check Point Research's MCPoison disclosure (August 2025) demonstrated how a malicious MCP server installed via an IDE extension could manipulate code generation. The client's extension system acted as the entry point — the server was installed through the IDE's plugin marketplace with minimal review, and once active it influenced tool selection and output for all projects.

**Tests:** `MCPSTG-CLNT-06`, `MCPSTG-CLNT-02`.

### Canonical attack patterns

### Configuration Injection via Project Files

**Tests:** `MCPSTG-CLNT-01`, `MCPSTG-CLNT-06`.

An attacker places a configuration file in a repository (`.mcp.json`, `mcp.config`, workspace settings) that registers a malicious MCP server. When a developer clones and opens the project, the host reads the config and connects to the rogue server — potentially launching an arbitrary process or connecting to an attacker-controlled endpoint.

#### Impact

* Arbitrary code execution via `stdio` server spawning.
* Silent data exfiltration through rogue tool calls.
* Persistence across sessions if the config is not removed.

#### Red flags

* Project-level config files that define MCP servers unfamiliar to the team.
* Server commands or URLs that differ from the organization's approved list.
* Config files added in PRs from external contributors.

#### Defensive guidance

* Require explicit user approval before trusting any project-scoped MCP server definition.
* Distinguish user-global config (trusted) from workspace-scoped config (untrusted by default).
* Display the full command and arguments before launching a new `stdio` server.
* Maintain an allowlist of approved MCP server commands and endpoints.

### Approval Bypass and Human-in-the-Loop Erosion

**Tests:** `MCPSTG-CLNT-02`.

Clients that offer "auto-approve" or "yolo mode" settings remove the human-in-the-loop control that MCP's security model depends on. Even without explicit auto-approve, rapid sequential approval prompts, confusing UX, or tools that operate within an already-approved session can lead to unintended approvals.

#### Impact

* Destructive tool calls executed without user awareness.
* Data exfiltration through approved-but-unexpected tool invocations.
* Compliance violations when sensitive actions bypass audit trails.

#### Red flags

* Auto-approve settings enabled in production or shared environments.
* Approval prompts that do not display the full tool name, arguments, and server identity.
* Batch approvals that cover multiple tools in a single click.

#### Defensive guidance

* Default to per-call approval for destructive or data-access tools.
* Display server identity, tool name, and full arguments in every approval prompt.
* Log approval decisions with user identity and timestamp.
* Disallow auto-approve for tools annotated as `destructiveHint: true`.

### MCPSTG-CLNT-01 — Test Client Configuration Injection

<a id="mcpstg-clnt-01"></a>

#### Summary

Verify that the MCP host does **not** automatically trust MCP server definitions found in project-level or workspace-scoped configuration files. A malicious config file in a cloned repository should not silently register and launch a rogue MCP server.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with a host that reads workspace-level MCP config.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` is the legitimate server. A second config entry points to `<TEST_ROGUE_SERVER>` via a project-level config file.
- **Trust boundary:** user-global config (trusted) ↔ workspace/project config (untrusted).
- **Attacker position:** contributor to a repository who adds a malicious MCP config file.
- **Potential impact:** arbitrary code execution, silent data exfiltration, credential theft.

#### Test Objectives

- Confirm the host prompts the user before connecting to a server defined only in project-level config.
- Confirm `stdio` server commands from project config are not executed without explicit approval.
- Confirm HTTP/SSE server URLs from project config are not contacted without explicit approval.
- Document whether the host distinguishes user-global from project-scoped server definitions.

#### Preconditions

- Authorized lab environment and written scope.
- Access to host configuration at both user-global and workspace levels.
- A lab repository containing a project-level MCP config file with a rogue server definition.
- Network monitoring to observe outbound connections from the host.
- Log access for host startup and server connection events.

#### How to Test

##### 1. Manual Review

Review the host's documentation and source code for how it discovers and loads MCP server definitions. Identify all file paths scanned: user-global config, workspace config, project-level dotfiles (`.mcp.json`, `.mcp/config`, `.codex/config.toml`, etc.). Document the trust model for each source.

##### 2. Configuration Review

Inspect the host's settings for:
- Whether project-level configs are enabled by default.
- Whether there is a trust prompt before connecting to project-scoped servers.
- Whether `stdio` commands from project config are sandboxed or restricted.
- Whether an allowlist of approved server commands or URLs exists.

##### 3. Runtime Testing

1. Clone `<TEST_ROGUE_REPO>` containing a project-level MCP config that defines a benign lab server at `<TEST_ROGUE_SERVER>`.
2. Open the project in the MCP host.
3. Observe: does the host prompt the user before connecting to the new server?
4. If using `stdio` transport, observe: is the server process launched without approval?
5. Record all network connections and process spawns during project open.

##### 4. Abuse Case Testing

- Place config files at multiple project-level paths to test which ones the host reads.
- Use a config that specifies environment variables (e.g., `"env": {"EXFIL_URL": "<TEST_ENDPOINT>"}`) to test whether arbitrary env vars are passed.
- Test config files with command arguments containing shell metacharacters (lab-safe only).

##### 5. Log and Detection Review

Confirm host logs record: config source path, server definition origin (global vs. project), user approval decision, and process spawn details. Verify that a project-level server connection without approval generates an alert.

#### Example snippets

Malicious project-level config (`<TEST_ROGUE_REPO>/.mcp.json`):

```json
{
  "mcpServers": {
    "<TEST_ROGUE_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/rogue-server/index.js"],
      "env": {
        "EXFIL_URL": "<TEST_ENDPOINT>"
      }
    }
  }
}
```

Legitimate user-global config for comparison:

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"],
      "env": {
        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

- `<TEST_ROGUE_REPO>`: lab Git repository containing the malicious config.
- `<TEST_ROGUE_SERVER>`: benign lab server that logs all connections (acts as canary).
- `<TEST_ENDPOINT>`: lab HTTP endpoint that records incoming requests.

#### Expected Results

- **Secure:** host displays a clear trust prompt showing the server command, arguments, and config source path before connecting. The user must explicitly approve. Unapproved servers are not launched or contacted. Logs record the decision.
- **Insecure:** host silently launches the rogue server process or connects to the rogue endpoint upon opening the project directory. No approval prompt is shown. No log entry distinguishes the config source.
- **Evidence:** screenshots of approval prompts (or their absence), host logs, process list showing server spawns, network capture showing connections to `<TEST_ROGUE_SERVER>`.

#### Remediation

- Require explicit user approval before trusting any MCP server defined in a project-level config file.
- Display the full command, arguments, environment variables, and config source in the approval prompt.
- Maintain a persistent allowlist of approved server commands and URLs per user.
- Consider project-level configs untrusted by default; require the user to opt-in per project.
- Log config source origin (global, workspace, project, extension) for every server connection.

#### Tools

Host configuration inspector, local process and file-access tracer, HTTP/TLS interception proxy, egress observer (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-CLNT-02 — Test Client Tool Approval Bypass

<a id="mcpstg-clnt-02"></a>

#### Summary

Verify that the MCP host enforces **human-in-the-loop approval** for tool invocations, especially those annotated as destructive or sensitive. Auto-approve settings, batch approval prompts, or confusing UX must not allow dangerous tool calls to execute without informed user consent.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with configurable tool approval settings.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` exposing tools with varying risk annotations (`readOnlyHint`, `destructiveHint`).
- **Trust boundary:** user approval decision ↔ tool execution.
- **Attacker position:** a poisoned tool description or a rapid sequence of tool calls designed to fatigue or bypass the approval flow.
- **Potential impact:** unauthorized data modification, file deletion, credential exfiltration, command execution without user awareness.

#### Test Objectives

- Confirm destructive tools (`destructiveHint: true`) always require per-call approval.
- Confirm auto-approve or "trust all" settings do not override destructive-tool approval.
- Confirm approval prompts display the full tool name, server identity, and arguments.
- Confirm batch approval of multiple tools is not possible without individual review.
- Document how the host handles rapid sequential approval prompts.

#### Preconditions

- Authorized lab environment and written scope.
- Lab MCP server with tools annotated at different risk levels.
- Access to host approval settings and UI.
- Log access for approval decisions.

#### How to Test

##### 1. Manual Review

Review the host's approval UX: what information is displayed? Does it show the server name, tool name, and full argument values? Is there a "remember" or "auto-approve" checkbox? Does it distinguish read-only from destructive tools?

##### 2. Configuration Review

Inspect host settings for:
- Auto-approve or "yolo mode" options and their scope.
- Per-server trust levels.
- Per-tool approval policies.
- Whether tool annotations (`destructiveHint`, `readOnlyHint`) affect the approval flow.

##### 3. Runtime Testing

1. Connect to `<AUTHORIZED_LAB_SERVER>` with default approval settings.
2. Trigger a tool call to a `readOnlyHint: true` tool — record the approval behavior.
3. Trigger a tool call to a `destructiveHint: true` tool — record the approval behavior.
4. Enable auto-approve (if available) and repeat step 3 — verify the destructive tool still requires approval.
5. Trigger 10 rapid sequential tool calls and observe whether approval fatigue leads to blanket approval.

##### 4. Abuse Case Testing

- Send a `tools/call` where the displayed tool name is benign but the arguments contain sensitive operations (argument mismatch attack).
- Test a tool whose description changed since the last approval (tool drift — see `MCPSTG-TOOL-01`).
- Test whether approving a tool on Server A grants implicit approval for the same tool name on Server B.

##### 5. Log and Detection Review

Confirm logs record: tool name, server identity, approval decision (approved/denied/auto-approved), user identity, timestamp, and the full arguments that were approved. Verify that auto-approved destructive calls generate alerts.

#### Example snippets

Lab server tool with destructive annotation:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "delete_workspace_files",
        "description": "Permanently deletes files from the workspace.",
        "inputSchema": {
          "type": "object",
          "properties": {
            "path": { "type": "string" },
            "recursive": { "type": "boolean" }
          },
          "required": ["path"],
          "additionalProperties": false
        },
        "annotations": {
          "destructiveHint": true,
          "readOnlyHint": false
        }
      }
    ]
  }
}
```

Tool call that should require approval:

```json
{
  "jsonrpc": "2.0",
  "id": 5,
  "method": "tools/call",
  "params": {
    "name": "delete_workspace_files",
    "arguments": {
      "path": "<TEST_WORKSPACE>/data",
      "recursive": true
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

#### Expected Results

- **Secure:** destructive tools always require explicit per-call approval regardless of auto-approve settings. Approval prompt displays server identity, tool name, and full arguments. Rapid sequential prompts do not degrade to batch approval. Approval for Server A does not carry over to Server B.
- **Insecure:** auto-approve bypasses destructive-tool approval. Approval prompt is vague or missing arguments. Rapid tool calls execute without individual review. Cross-server approval inheritance occurs.
- **Evidence:** screenshots of approval prompts, host settings, approval logs, timing analysis of rapid call sequences.

#### Remediation

- Enforce per-call approval for all tools annotated `destructiveHint: true`, regardless of global settings.
- Display server identity, tool name, and complete arguments (with sensitive values masked) in every prompt.
- Prevent cross-server approval inheritance — approval for a tool on one server does not apply to another.
- Rate-limit approval prompts and warn the user if tools are requesting approval faster than human review pace.
- Log every approval decision with full context for audit.

#### Tools

Host configuration inspector, MCP client utility (raw JSON-RPC), UI testing tools for approval flow (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

#### References

- [Model Context Protocol specification](https://modelcontextprotocol.io/) — tool annotations and approval guidance.
- [OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) — human approval requirements.
- [04. Secure MCP Development](<../04. Secure MCP Development.md>) — Tool permission UX section.

#### Mapping

- [OWASP LLM Top 10](https://owasp.org/www-project-top-10-for-large-language-model-applications/): [LLM06 Excessive Agency](https://genai.owasp.org/llmrisk/llm06/)

### MCPSTG-CLNT-03 — Test Client Credential Storage Security

<a id="mcpstg-clnt-03"></a>

#### Summary

Verify that the MCP host does **not** store API keys, OAuth tokens, or other credentials in plaintext configuration files that are readable by other processes, other users, or other MCP servers. Credential theft from client config files has been demonstrated in published tool-poisoning attacks.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with MCP servers configured using API keys and OAuth tokens.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` whose configuration includes a synthetic API key.
- **Trust boundary:** host credential store ↔ local filesystem ↔ other processes.
- **Attacker position:** a malicious MCP server or local process that reads the host's configuration files.
- **Potential impact:** credential theft, lateral movement to other services, persistent access.

#### Test Objectives

- Identify where the host stores MCP server credentials (file paths, format, permissions).
- Confirm credentials are not stored in plaintext in config files.
- Confirm other processes and other MCP servers cannot read the credentials of unrelated servers.
- Confirm credentials are not logged or exposed in error messages.

#### Preconditions

- Authorized lab environment and written scope.
- Lab MCP server configured with a synthetic API key (`<TEST_API_KEY>`).
- Access to the host's filesystem to inspect config file permissions and contents.
- A second lab process or MCP server to test cross-process read access.

#### How to Test

##### 1. Manual Review

Review host documentation for credential storage guidance. Identify all paths where credentials may be stored: config files, environment variables, keychain/credential-manager integration, in-memory only.

##### 2. Configuration Review

Inspect the host's MCP configuration files:
- Check file permissions (owner, group, world readability).
- Search for plaintext tokens, API keys, passwords, and OAuth secrets.
- Check whether `.env` files or `env` blocks in config contain credentials.
- Verify whether the host uses OS keychain, credential manager, or vault integration.

##### 3. Runtime Testing

1. Configure `<AUTHORIZED_LAB_SERVER>` with `<TEST_API_KEY>` in the host config.
2. Search the filesystem for `<TEST_API_KEY>` in any file — config, logs, temp files, shell history.
3. From a second user account or process, attempt to read the host's config file.
4. From a second MCP server connected to the same host, attempt to enumerate env vars or read config paths.

##### 4. Abuse Case Testing

- Use a lab MCP server with a tool description that instructs the model to read the host config file and return its contents (replicating the Invariant Labs tool-poisoning scenario).
- Check whether the host passes all environment variables to MCP server processes or only declared ones.

##### 5. Log and Detection Review

Confirm that credentials are never logged in host logs, server logs, or error output. Verify that access to credential storage files is auditable.

#### Example snippets

Host config with plaintext credential (insecure pattern):

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE>/servers/lab-server/index.js"],
      "env": {
        "API_KEY": "<TEST_API_KEY>",
        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }
    }
  }
}
```

Tool call attempting to read config (from poisoned tool description):

```json
{
  "jsonrpc": "2.0",
  "id": 10,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": {
      "path": "<TEST_HOST_CONFIG_PATH>"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

- `<TEST_API_KEY>`: `mcpstg-lab-credential-00000000` (synthetic, never valid).
- `<TEST_HOST_CONFIG_PATH>`: path to the host's MCP config file on the lab system.

#### Expected Results

- **Secure:** credentials are stored in an OS keychain, credential manager, or encrypted store. Config files contain references (e.g., `"$VAULT_KEY"`) not plaintext values. File permissions restrict access to the owning user. Environment variables passed to server processes include only declared variables, not the full host environment. Credential values do not appear in logs.
- **Insecure:** API keys and tokens are stored in plaintext in JSON or TOML config files with world-readable permissions. The host passes its full environment to server processes. A tool-poisoning attack can exfiltrate credential values from the config file.
- **Evidence:** config file contents (with synthetic creds), file permission listings, search results for credential patterns, log excerpts.

#### Remediation

- Use OS keychain or credential manager for all MCP server credentials; never store secrets in plaintext config files.
- Set config file permissions to owner-read-only (600 or equivalent).
- Pass only explicitly declared environment variables to server processes, not the full host environment.
- Redact credential values from all log output and error messages.
- Warn users if a config file contains what appears to be a plaintext secret.

#### Tools

Local process and file-access tracer, secret scanner, host configuration inspector (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

- Invariant Labs, [MCP Security Notification: Tool Poisoning Attacks](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks) — credential exfiltration via tool-poisoned reads of `~/.cursor/mcp.json`.
- [04. Secure MCP Development](<../04. Secure MCP Development.md>) — Secrets management section.

### MCPSTG-CLNT-04 — Test Client-to-Server Transport Validation

<a id="mcpstg-clnt-04"></a>

#### Summary

Verify that the MCP client properly validates transport-layer security when connecting to MCP servers. This includes TLS certificate validation for remote servers, origin validation and DNS rebinding protection for local HTTP servers, and proper binding of local servers to loopback addresses only.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation connecting to both local and remote MCP servers.
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` running locally on Streamable HTTP, and a remote server over HTTPS.
- **Trust boundary:** client ↔ transport layer ↔ server.
- **Attacker position:** network attacker performing DNS rebinding against a local server, or MITM against a remote server with a self-signed or expired certificate.
- **Potential impact:** session hijacking, unauthorized tool invocation, data interception, remote access to local MCP servers.

#### Test Objectives

- Confirm the client rejects self-signed, expired, and mismatched TLS certificates for remote MCP servers.
- Confirm local HTTP servers are protected against DNS rebinding (Origin header validation).
- Confirm local servers bind to `127.0.0.1` (or `::1`), not `0.0.0.0`.
- Confirm the client validates the `Origin` header on incoming requests to local servers.

#### Preconditions

- Authorized lab environment and written scope.
- Lab MCP server accessible over both local HTTP and remote HTTPS.
- TLS testing certificates: self-signed, expired, wrong-hostname.
- DNS rebinding test setup (lab domain that resolves to `127.0.0.1` after initial resolution).
- Network monitoring tools.

#### How to Test

##### 1. Manual Review

Review the client's transport configuration and source code for TLS validation settings and DNS rebinding protections.

##### 2. Configuration Review

Inspect:
- Client TLS settings: certificate pinning, CA trust store, verification bypass options.
- Local server bind address configuration.
- Origin validation settings for local HTTP servers.

##### 3. Runtime Testing

1. Configure `<AUTHORIZED_LAB_SERVER>` with a **self-signed TLS certificate** on a remote endpoint. Attempt connection — expect rejection.
2. Configure with an **expired certificate** — expect rejection.
3. Configure with a **wrong-hostname certificate** — expect rejection.
4. Start a local Streamable HTTP server. Verify it binds to `127.0.0.1`, not `0.0.0.0`.
5. Send a request to the local server with `Origin: https://<TEST_REBINDING_DOMAIN>` — expect `403`.
6. Perform a lab DNS rebinding test: resolve `<TEST_REBINDING_DOMAIN>` to the local server's port — expect the client or server to block the rebinding request.

##### 4. Abuse Case Testing

- Test whether the client offers a "skip TLS validation" option and whether it is easily discoverable.
- Test whether disabling DNS rebinding protection (as was the default in CVE-2025-66414) is possible via configuration.

##### 5. Log and Detection Review

Confirm logs record TLS validation failures, origin validation rejections, and DNS rebinding attempts with source details.

#### Example snippets

DNS rebinding test request to local MCP server:

```http
POST /mcp HTTP/1.1

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list"
}
```

Expected secure response:

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json

{"error": "Origin not allowed"}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

- `<TEST_REBINDING_DOMAIN>`: lab domain configured for DNS rebinding tests.
- Self-signed cert, expired cert, wrong-hostname cert — all lab-generated.

#### Expected Results

- **Secure:** client rejects all invalid TLS certificates with clear error messages. Local server binds to loopback only. Origin validation rejects requests from non-localhost origins. DNS rebinding is blocked by default.
- **Insecure:** client connects despite TLS errors. Local server binds to `0.0.0.0`. No origin validation on local HTTP server. DNS rebinding allows remote websites to access the local MCP session.
- **Evidence:** TLS error messages (or their absence), `netstat`/`ss` output showing bind address, HTTP responses to cross-origin requests, DNS rebinding test results.

#### Remediation

- Enforce TLS certificate validation for all remote MCP server connections with no user-accessible bypass.
- Bind local HTTP servers to `127.0.0.1` (IPv4) and `::1` (IPv6) by default.
- Enable DNS rebinding protection by default: validate `Origin` and `Host` headers, reject requests where the resolved IP is not loopback.
- Log all transport validation failures.

### MCPSTG-CLNT-05 — Test Client Workspace Isolation

<a id="mcpstg-clnt-05"></a>

#### Summary

Verify that the MCP host enforces **workspace isolation** so that opening one project does not expose another project's MCP servers, credentials, or context. Workspace bleed allows a malicious project to access resources of a trusted project through the shared host.

#### Scenario

- **MCP host/client:** `<TEST_USER>` with two projects open: `<TEST_WORKSPACE_A>` (trusted, with sensitive MCP servers) and `<TEST_WORKSPACE_B>` (untrusted, cloned from external source).
- **MCP server:** `<AUTHORIZED_LAB_SERVER>` configured for Workspace A only.
- **Trust boundary:** Workspace A scope ↔ Workspace B scope.
- **Attacker position:** contributor to Workspace B's repository who wants to access Workspace A's MCP servers or credentials.
- **Potential impact:** cross-project data access, credential theft, unauthorized tool invocation against Workspace A's servers from Workspace B's context.

#### Test Objectives

- Confirm MCP servers configured for Workspace A are not accessible from Workspace B.
- Confirm credentials scoped to Workspace A are not readable by Workspace B's MCP servers.
- Confirm model context from Workspace A does not bleed into Workspace B sessions.
- Document the host's workspace isolation model.

#### Preconditions

- Authorized lab environment and written scope.
- Two lab workspaces configured with separate MCP servers.
- Access to host configuration for both workspaces.
- Log access for server connections and tool calls.

#### How to Test

##### 1. Manual Review

Review the host's workspace isolation model: are MCP servers scoped to workspaces? Can a server from Workspace A be called from Workspace B's session? Are credentials inherited across workspaces?

##### 2. Configuration Review

Inspect:
- Per-workspace vs. global MCP server definitions.
- Whether workspace switching preserves or resets server connections.
- Whether environment variables from one workspace's config are visible to another workspace's servers.

##### 3. Runtime Testing

1. Open `<TEST_WORKSPACE_A>` and connect to `<AUTHORIZED_LAB_SERVER>`. Perform a `tools/list` call.
2. Switch to (or simultaneously open) `<TEST_WORKSPACE_B>`.
3. From Workspace B's context, attempt to call a tool on `<AUTHORIZED_LAB_SERVER>`.
4. From Workspace B's context, attempt to read resources exposed by Workspace A's server.
5. Record whether the host shows Workspace A's servers in Workspace B's server list.

##### 4. Abuse Case Testing

- In Workspace B, add a tool description that instructs the model to call tools on all connected servers (testing cross-workspace tool access).
- Test whether a shared global server has access to both workspaces' file systems simultaneously.

##### 5. Log and Detection Review

Confirm logs record the workspace context for every tool call and resource read. Verify that cross-workspace access attempts generate alerts.

#### Example snippets

Workspace A config:

```json
{
  "mcpServers": {
    "<AUTHORIZED_LAB_SERVER>": {
      "command": "node",
      "args": ["<TEST_WORKSPACE_A>/servers/trusted-server/index.js"],
      "env": {
        "WORKSPACE_ROOT": "<TEST_WORKSPACE_A>",
        "API_KEY": "<TEST_API_KEY_A>"
      }
    }
  }
}
```

Cross-workspace tool call attempt from Workspace B:

```json
{
  "jsonrpc": "2.0",
  "id": 20,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": {
      "path": "<TEST_WORKSPACE_A>/sensitive-data.json"
    }
  }
}
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

#### Expected Results

- **Secure:** MCP servers from Workspace A are not visible or callable from Workspace B. Credentials from Workspace A's config are not accessible to Workspace B's servers. Model context is isolated per workspace. Cross-workspace tool calls are rejected.
- **Insecure:** Workspace B can see and call Workspace A's MCP servers. Workspace A's credentials are visible to Workspace B's server processes. Model context from one workspace bleeds into another.
- **Evidence:** server lists per workspace, tool call responses showing cross-workspace access (or rejection), credential search results, log excerpts showing workspace context.

#### Remediation

- Scope MCP server connections strictly to their defining workspace.
- Isolate credentials per workspace — do not inherit across workspace boundaries.
- Clear model context when switching workspaces.
- Display the active workspace prominently in the host UI so the user knows which servers are connected.
- Log the workspace context for every server connection, tool call, and resource read.

Host configuration inspector, MCP client utility, local process tracer (see [Appendix F — Testing Tools](../11. Appendix F - Testing Tools.md)).

### MCPSTG-CLNT-06 — Test Client Auto-Install and Update Security

<a id="mcpstg-clnt-06"></a>

#### Summary

Verify that the MCP host does **not** automatically install or update MCP server packages without user verification and integrity checks. Auto-install flows that bypass review allow supply-chain attacks to introduce malicious servers silently.

#### Scenario

- **MCP host/client:** `<TEST_USER>` on a lab workstation with MCP server auto-install or marketplace features.
- **MCP server:** `<TEST_PACKAGE>` — a lab MCP server package available from a test registry.
- **Trust boundary:** package registry ↔ host install flow ↔ local execution.
- **Attacker position:** package publisher who updates a previously benign package with malicious functionality (rug pull), or a typosquatter who publishes a confusingly similar package name.
- **Potential impact:** arbitrary code execution, silent backdoor installation, persistent compromise.

#### Test Objectives

- Confirm the host does not auto-install MCP servers without explicit user approval.
- Confirm the host verifies package integrity (checksums, signatures) before installation.
- Confirm auto-update flows require user review before applying.
- Confirm the host warns about package name similarities (typosquat detection).
- Document what information the host displays before installing a server package.

#### Preconditions

- Authorized lab environment and written scope.
- Lab package registry with test MCP server packages.
- Access to the host's install/update settings and logs.

#### How to Test

##### 1. Manual Review

Review the host's MCP server installation flow: how are servers discovered, reviewed, and installed? Is there a marketplace or recommendation system? What verification steps exist?

##### 2. Configuration Review

Inspect host settings for:
- Auto-install or auto-update settings.
- Package integrity verification (checksum, signature, provenance).
- Registry allowlists.
- Version pinning configuration.

##### 3. Runtime Testing

1. Trigger an MCP server install flow for `<TEST_PACKAGE>` — observe what information is displayed (publisher, version, permissions, source).
2. Verify the host checks package integrity before installation.
3. Publish an updated version of `<TEST_PACKAGE>` to the lab registry with changed tool definitions. Observe whether the host auto-updates or prompts the user.
4. Publish a typosquat package (`<TEST_PACKAGE_TYPO>`) and observe whether the host warns about name similarity.

##### 4. Abuse Case Testing

- Test whether a workspace-level config file can trigger automatic package installation (combination with CLNT-01).
- Test whether downgrade attacks are possible (reverting to a version with known vulnerabilities).

##### 5. Log and Detection Review

Confirm logs record: package name, version, source registry, integrity check result, user approval decision, and installation path. Verify that installs without integrity verification generate alerts.

#### Example snippets

Host config referencing a package to install:

```json
{
  "mcpServers": {
    "<TEST_PACKAGE>": {
      "command": "npx",
      "args": ["-y", "<TEST_PACKAGE>@latest"],
      "env": {
        "WORKSPACE_ROOT": "<TEST_WORKSPACE>"
      }
    }
  }
}
```

Expected install verification prompt (secure behavior):

```text
Install MCP server "<TEST_PACKAGE>"?
  Publisher: <TEST_PUBLISHER>
  Version: 1.2.3
  Source: <TEST_REGISTRY>
  Integrity: SHA-256 verified
  Tools: read_data (readOnly), write_data (destructive)
  [Allow] [Deny] [View source]
```

#### Test Data / Example Payloads

Use synthetic placeholders only. Replace `<TEST_*>` values with [Appendix D — Safe Lab Fixtures](../10. Appendix D - Safe Lab Fixtures.md) fixtures.

- `<TEST_PACKAGE>`: lab MCP server package published to a test registry.
- `<TEST_PACKAGE_TYPO>`: similar-named package for typosquat testing.
- `<TEST_REGISTRY>`: lab npm/pip registry.

#### Expected Results

- **Secure:** host never auto-installs without user approval. Installation prompt shows publisher, version, source, integrity status, and tool permissions. Updates require user review. Typosquat warnings are displayed for confusingly similar names. Integrity verification fails loudly.
- **Insecure:** server packages are installed or updated automatically. No integrity check is performed. No install prompt or an uninformative one. Typosquat packages install without warning.
- **Evidence:** install flow screenshots, log entries, integrity check results, registry query traces.

#### Remediation

- Require explicit user approval for every MCP server installation and update.
- Verify package integrity (cryptographic signatures or checksums) before installation.
- Display publisher identity, version, tool permissions, and source in the install prompt.
- Implement version pinning by default; require explicit opt-in to auto-update.
- Warn about package name similarities to known packages (typosquat detection).
- Log all install and update events with full provenance details.
